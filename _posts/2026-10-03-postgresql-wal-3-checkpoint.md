## 1. 체크포인트(Checkpoint)란?

PostgreSQL은 데이터가 변경될 때마다 매번 디스크 데이터 파일에 즉시 쓰지 않는다. **메모리(Shared Buffer)의 페이지만 수정하고, 변경 내용은 WAL에 순차적으로 기록**한 뒤, 디스크 데이터 파일에는 나중에 일괄 반영한다. 이렇게 메모리에서 수정되었지만 아직 디스크 데이터 파일에 쓰이지 않은 페이지를 **Dirty 페이지**라고 부른다.

서버에 장애가 발생해 메모리가 날아가더라도, 디스크에 안전하게 저장된 WAL을 순차적으로 다시 적용(Redo)하면 유실 없이 데이터를 복구할 수 있다. 

하지만 서버가 운영된 지 몇 달, 몇 년이 지났는데 장애 복구 시 WAL을 첫날부터 전부 다시 읽어 적용할 수는 없다. 복구에 엄청난 시간이 걸릴 뿐 아니라 디스크 공간도 무한정 낭비되기 때문이다.

따라서 PostgreSQL은 주기적으로 **"이 위치 이전의 모든 변경 사항은 디스크 데이터 파일에 안전하게 반영 완료되었다"**라는 보장 기준점을 만드는데, 이 동기화 작업이 바로 **체크포인트(Checkpoint)**이며, 그 복구 기준 위치(LSN)를 **Redo 포인트**라고 부른다.

> ⚠️ **주의 (흔한 오해 바로잡기)**  
> 체크포인트는 WAL 로그를 읽어서 디스크 데이터 파일에 반영하는 작업이 아니다.  
> **메모리(Shared Buffer)에 머물러 있는 Dirty 페이지들을 디스크의 실제 데이터 파일로 플러시(Flush)하는 작업**이다.  
> WAL을 읽는 작업은 평상시가 아니라 **장애 발생 후 크래시 복구(Crash Recovery)를 진행할 때만** 발생한다.

## 2. 체크포인트 진행 순서 4단계

체크포인트는 시스템 부하를 최소화하기 위해 백그라운드에서 신중하게 단계별로 진행된다.

1. **시작 (Start)**: 현재 시점의 WAL 위치(LSN)를 조사하여 **Redo 포인트 후보**로 메모해 둔다. (트랜잭션을 멈추거나 테이블 락을 거는 것이 아니라, 단지 현재 위치만 메모해 둔다.)
2. **태그 (Tag)**: 이 시점에 메모리(Shared Buffer)에 존재하는 모든 Dirty 페이지에 "이번 체크포인트에서 디스크로 보낼 대상"이라는 표식을 붙인다.
3. **저장 (Write & Fsync)**: 표식이 붙은 페이지만 조금씩 나누어 천천히 디스크 파일에 기록한다(`checkpoint_completion_target` 설정에 따라 점진적으로 I/O를 분산). 이 작업 도중 새로 변경되어 Dirty가 된 페이지는 이번 체크포인트 대상이 아니며, 다음 체크포인트의 몫이 된다.
4. **완료 (Finish)**: 모든 표식 페이지의 디스크 저장이 끝나면 체크포인트 완료 레코드를 WAL에 기록하고, 제어 파일인 `pg_control`에 새로운 **Redo 포인트를 갱신 확정**한다.

## 3. 크래시 복구(Crash Recovery)의 2가지 핵심 규칙

서버가 비정상 종료된 후 다시 시작될 때 PostgreSQL은 다음 2가지 규칙을 통해 데이터를 안전하게 복구한다.

1. **어느 체크포인트를 기준으로 복구할 것인가?**  
   도중에 장애가 나서 멈춘 불완전한 체크포인트는 무시하고, **정상적으로 완전히 끝난 마지막 체크포인트**만을 신뢰한다.
2. **그 체크포인트의 어디서부터 Redo를 시작할 것인가?**  
   체크포인트 완료 지점이 아니라, **체크포인트 시작 지점(Redo 포인트)**부터 WAL을 읽어 재실행한다. 체크포인트가 수행되는 수 분 동안 백그라운드에서 새로운 트랜잭션이 페이지를 수정했을 수 있고, 그 페이지는 아직 디스크에 쓰이지 않았을 수 있기 때문이다.

## 4. [비유] 학생의 숙제 비유로 이해하기

체크포인트와 복구 매커니즘을 숙제하는 학생의 일상에 비유해 보면 훨씬 쉽게 와닿는다.

| 비유 요소 | PostgreSQL 대응 개념 | 역할 설명 |
| :--- | :--- | :--- |
| **연습장** | Shared Buffer (메모리) | 언제 버려질지 모르는 임시 작업 공간 |
| **숙제 공책** | 데이터 파일 (디스크) | 최종 제출해야 하는 공식 영구 기록물 |
| **일기장** | WAL (Write Ahead Log) | 한 일(변경 작업)을 발생 순서대로 한 줄씩 적는 곳 |
| **일기장에 그은 "정리 시작" 밑줄** | Redo 포인트 | 이 줄 이전 내용은 공책에 확실히 다 옮겨 적었음을 나타냄 |
| **책상 앞 포스트잇 쪽지** | `pg_control` 제어 파일 | "밑줄 이전 내용은 공책에 다 옮겨 적었음"을 명시하는 기준표 |

학생은 문제를 풀 때 먼저 연습장(메모리)에 끄적이고 일기장(WAL)에 기록한다. 그러다 가끔씩 일기장에 밑줄(Redo 포인트)을 긋고, 연습장 내용을 정성껏 숙제 공책(데이터 파일)으로 옮겨 적기 시작한다. **공책에 모든 내용을 다 옮겨 적고 나서야** 비로소 책상 앞 쪽지(pg_control)를 새 위치로 교체한다. 

만약 엄마가 들어와 연습장을 버려버려도(서버 크래시), 학생은 책상 쪽지에 적힌 줄(Redo 포인트)부터 일기장을 다시 읽어 공책에 복원할 수 있다.

## 5. [실습] pg_control_checkpoint() 로 체크포인트 직접 검증

PostgreSQL의 제어 파일에 기록된 체크포인트 상태는 다음 함수로 직접 확인할 수 있다.

```sql
SELECT 
    checkpoint_lsn, 
    redo_lsn, 
    redo_wal_file, 
    timeline_id, 
    checkpoint_time
FROM pg_control_checkpoint();
```

![image-20261003114950096](/images/postgresql-wal-mechanism/img_8.png)

실제 수동으로 `CHECKPOINT;` 명령을 수행하기 전과 후를 비교해 보면:

| 항목 | CHECKPOINT 전 | CHECKPOINT 후 | 설명 |
| :--- | :---: | :---: | :--- |
| **redo_lsn** | `0/E000148` | `0/E0001F8` | 복구를 시작할 기준점이 앞으로 전진함 |
| **checkpoint_lsn** | `0/E000148` | `0/E000230` | 체크포인트 완료 레코드가 기록된 WAL 위치 |

- **`redo_lsn` 전진**: 체크포인트 완료 후 복구 시작 지점이 더 최신 위치로 당겨졌다. 이제 장애가 나더라도 `0/E0001F8` 이후의 WAL만 읽으면 되므로 복구 시간이 크게 단축된다.
- **`redo_lsn < checkpoint_lsn`**: 체크포인트를 시작할 때 기억해 둔 Redo 위치와 모든 Dirty 페이지 flush 완료 후 체크포인트 레코드를 기록한 위치 사이에 간격이 발생했음을 보여준다.
- **무부하 상태 건너뛰기**: 만약 데이터 변경 작업이 전혀 발생하지 않았다면, PostgreSQL은 `checkpoint_timeout`이 경과하더라도 불필요한 체크포인트를 자동으로 건너뛴다.

## 6. WAL 세그먼트 파일 관리와 디스크 제어

체크포인트가 성공적으로 끝나 새로운 Redo 포인트가 확정되면, **그 이전의 Redo 포인트가 포함된 과거 WAL 세그먼트 파일들은 장애 복구 관점에서 더 이상 필요 없어진다.** 

PostgreSQL은 이 불필요해진 세그먼트 파일들을 즉시 삭제하거나 미래에 쓸 파일로 **재활용(Recycle)**한다.

이 세그먼트 파일 유지 및 정리는 `min_wal_size`와 `max_wal_size` 설정에 의해 제어된다.

| 설정 파라미터 | 기본값 | 주요 역할 및 특징 |
| :--- | :---: | :--- |
| **min_wal_size** | 80MB (약 5개 파일) | 디스크에 항상 유지할 WAL 파일의 최소 총량. 대량 배치 작업 시 파일 생성/삭제 I/O 반복을 방지하기 위해 이 크기만큼은 파일을 삭제하지 않고 재활용한다. |
| **max_wal_size** | 1GB (약 64개 파일) | `pg_wal` 디렉토리가 차지할 수 있는 소프트 상한선(Soft Limit). WAL 사용량이 이 크기에 근접하면 PostgreSQL이 자동으로 즉시 체크포인트를 트리거한다. |

- **`max_wal_size`가 너무 큰 경우**: 많은 WAL을 유지할 수 있어 체크포인트 주기가 길어지고 평상시 I/O는 줄어들지만, 크래시 발생 시 다시 적용(Redo)해야 할 WAL 양이 많아져 **데이터베이스 복구 시간이 오래 걸린다.**
- **`max_wal_size`가 너무 작은 경우**: WAL 파일이 빠르게 차올라 체크포인트가 지나치게 자주 발생하며, 과도한 디스크 쓰기로 인해 DB 병목(Hang 현상)이 발생할 수 있다.

### WAL 세그먼트의 생명주기 및 재활용 과정

```
[1] WAL이 지속적으로 쌓이는 중
    Redo Point
    ↓
    [WAL_10][WAL_11][ ... ][WAL_18]
    └──────── max_wal_size 이내 ────────┘
    → Redo Point가 WAL_10에 걸쳐 있어 10~18번 파일이 모두 보존되어야 함

[2] 파일이 모두 차서 새 세그먼트 생성
    [WAL_10][WAL_11][ ... ][WAL_18][WAL_19]
                                    ↑ 새로 생성
    → 재활용 가능한 과거 파일이 없으므로 WAL_19를 디스크에 신규 할당
    → WAL 용량이 max_wal_size에 근접하여 체크포인트 트리거

[3] 체크포인트 완료 후 과거 세그먼트 재사용(Recycle)
                               New Redo Point
                                     ↓
    [WAL_10][WAL_11][ ... ][WAL_18][WAL_19][WAL_20][WAL_21]...
    └────── 필요 없어진 구간 ──────┘          ↑       ↑
         │       │                           │       │
         │       └───── 미래 파일로 재사용 (11 → 21) ─┘
         └───────────── 미래 파일로 재사용 (10 → 20) ────────┘
    → Redo Point가 WAL_19로 전진
    → WAL_10과 WAL_11은 삭제하지 않고 이름을 바꾸어 WAL_20, WAL_21로 즉시 재활용
```

## 7. 지속적 아카이빙(Continuous Archiving)과 PITR

데이터베이스의 `pg_wal` 디렉토리는 디스크 용량 한계 때문에 최소한의 최신 파일들만 보존하고 오래된 세그먼트를 덮어쓰거나 재활용한다.

하지만 만약 **일주일 전 특정 시점, 혹은 어제 오후 2시 실수로 `DROP TABLE`을 수행하기 직전 시점**으로 데이터베이스를 되돌려야 한다면 어떻게 해야 할까? 로컬 `pg_wal`에는 이미 그 시점의 WAL 파일이 삭제되었기 때문에 불가능하다.

이런 상황에 대비하여, 가득 찬 WAL 세그먼트 파일이 재활용되거나 삭제되기 전에 **원격 스토리지나 백업 디스크 영역으로 안전하게 복사해 두는 기술**을 **지속적 아카이빙(Continuous Archiving)**이라고 부른다.

- **archiver 백그라운드 프로세스**: WAL 세그먼트 파일이 16MB를 다 채우고 닫힐 때마다 이를 감지하여 아카이브 스크립트를 구동한다.
- **archive_command**: `postgresql.conf`에서 정의한 쉘 명령어로, 완료된 세그먼트 파일을 백업 스토리지(NFS, S3 등)로 복사한다.
- **아카이브 로그(Archive Log)**: 아카이브 영역에 안전하게 복사·보관된 과거 WAL 파일들을 의미한다.

베이스 백업(Base Backup) 파일 하나와 연속적으로 누적된 아카이브 로그만 보관되어 있다면, 사용자가 원하는 과거의 그 어떤 임의의 초 단위 시점으로도 데이터베이스를 완벽하게 재생·복원할 수 있는 **PITR(Point-in-Time Recovery)**이 가능해진다.

### 아카이빙 동작 흐름

```
[1] WAL_7 세그먼트 파일에 로그 기록 중
                                   current LSN
                                        ↓
    WAL 세그먼트     [WAL_5][WAL_6][WAL_7]       ← WAL_7에 실시간 기록 중
    아카이브 영역    [ ... ][LOG_5][LOG_6]
    → 이미 닫힌 WAL_5, WAL_6은 아카이브 디렉토리로 복사 완료
    → 현재 작성 중인 WAL_7은 아직 복사 대기

[2] WAL_7이 16MB를 다 채우고 WAL_8로 스위치
                                           current LSN
                                                ↓
    WAL 세그먼트     [WAL_5][WAL_6][WAL_7][WAL_8] ← WAL_8 신규 오픈
                                 │
                                 ↓ archive_command 복사 실행
    아카이브 영역    [ ... ][LOG_5][LOG_6][LOG_7]
    → 닫힌 WAL_7이 아카이브 영역에 LOG_7로 안전하게 영구 복제됨
```

## 8. 마무리 및 요약

총 3편의 시리즈를 통해 PostgreSQL의 WAL과 관련된 핵심 메커니즘을 모두 살펴보았다.

1. **[1편] WAL 동작 원리와 구조**: Shared Buffer와 WAL Buffer의 상호작용, 트랜잭션 커밋 시 순차 쓰기를 통한 무결성 보장 및 8KB 페이지 / 레코드 계층 구조
2. **[2편] LSN과 추적 함수**: 64비트 주소 체계와 도서관 비유, `pg_current_wal_lsn()`, `pg_walfile_name()`, `pg_wal_lsn_diff()` 등 모니터링 함수와 복제 지연 측정
3. **[3편] 체크포인트와 아카이빙**: Dirty 페이지 디스크 플러시, Redo 포인트 기준 복구 원리, `max_wal_size` 기반 세그먼트 재활용, PITR을 위한 Continuous Archiving

이러한 유기적인 설계 덕분에 PostgreSQL은 고성능의 동시 트랜잭션 처리 속도를 유지하면서도 어떤 비정상 종료 상황에서도 단 1바이트의 커밋 데이터도 잃지 않는 강력한 ACID 무결성을 달성할 수 있다.
