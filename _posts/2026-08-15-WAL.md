데이터 무결성은 데이터에 대한 정확성, 일관성, 유효성을 의미한다.

정확성은 데이터 중복이 발생하거나 누락되지 않은 상태, 일관성은 원인과 결과가 연속적으로 보장되어 변하지 않은 상태를 의미한다.

데이터베이스 장애가 발생하면 RAM의 경우는 휘발성 데이터를 저장하기 때문에 손실하게 되어 무결성을 보장할 수 없게 된다. 무결성을 보장하려면 영구적인 공간인 디스크에 지속적으로 저장해야된다.

PostgreSQL에서는 데이터 변경이 먼저 RAM의 버퍼에 반영된 후 디스크에 일괄적으로 기록된다. 하지만 변경된 모든 페이지가 순차적으로 디스크에 기록되는 것은 아니므로, 이것만으로는 데이터의 일관성을 보장할 수 없다.

이런 상황에서 데이터 무결성을 보장하기 위해 WAL 방식을 사용하는데 **Write Ahead Log** 를 줄어서 말하며 문자의미로는 *먼저 로그에 기록한다* 라는 의미이다.

순차적으로 설명

1. 데이터 변경 발생

2. 메모리 영역인 Shared Buffer에 데이터 변경 진행

3. 동시에 WAL Buffer에 **데이터 변경 내용에 대한 로그(WAL Record) 기록**

4. Shared Buffer에 데이터 변경 완료

5. **WAL Buffer의 WAL Record를 WAL Segment에 기록하고 flush**

6. 데이터 파일에 최종 저장

위에서 동작 정리를 해보았는데 이해가 안되서 GPT도움으로 WAL 동작에 대해서 이해하기 쉽게 테스트할 수 있도록 코드를 짜달라고 해보았다.

1. 테스트 테이블 생성 및 데이터 주입

```sql
CREATE TABLE wal_test (
    id int PRIMARY KEY,
    name text
);

INSERT INTO wal_test VALUES (1, 'before');
```

2. 현재 WAL 위치 확인

```sql
SELECT
 pg_current_wal_insert_lsn() AS wal_insert,
 pg_current_wal_flush_lsn() AS wal_flush;
```

결과

3. 트랜잭션을 시작하고 데이터를 수정(커밋하지 말기!)

```sql
BEGIN;

UPDATE wal_test
SET name = 'after'
WHERE id = 1;
```

4. 커밋하지 않은 상태에서 WAL 위치 확인

```sql
SELECT
 pg_current_wal_insert_lsn() AS wal_insert,
 pg_current_wal_flush_lsn() AS wal_flush;
```

결과

![](/images/postgresql-wal-mechanism/img_2.png)

첫번째 첨부사진의 값이 달라진것으로 확인됨에 따라 WAL 가 업데이트 됨을 알 수 있다.

5. 커밋

```sql
COMMIT;
```

6. 커밋후 WAL 위치 확인

```sql
SELECT
 pg_current_wal_insert_lsn() AS wal_insert,
 pg_current_wal_flush_lsn() AS wal_flush;
```

만약에 변경된 데이터들을 장애로 인해 반영하지 못했다면 WAL 세그먼트 파일을 이용해서 데이터를 최신화 할 수 있다.

로그들은 append 방식으로 많은 디스크 IO를 발생시키지 않는다.

# pg_wal 디렉토리

pg_wal 디렉토리에 있는 wal 세그먼트 파일명은 아래 형태이다.

그중에 하나를 예시를 들어보자.

```
00000001 00000000 0000000B
──────── ──────── ────────
Timeline Log ID   Segment ID
```

## 앞자리 8자리

앞자리 8자리는(`00000001`) 타임라인id를 의미한다. 말그대로 타임라인을 위한 값이며 해당 값을 이용해서 PITR(Point-In-Time-Recovery)를 적용할 수 있다.부호없는 4바이트 정수이다.

## 중간 8자리

그 다음 8자리(`00000000`)는 **Log ID**이며, WAL 내부 위치를 나타내기 위한 값이다.(논리적인 LSN, **Long Sequence Number**)
많은 WAL 세그먼트가 계속 생성되므로, WAL 전체를 큰 구간으로 나누고 해당 세그먼트가 어느 구간에 위치하는지 구분하기 위한 값이라고 보면 된다.

```
[ Log ID 0 ] <----- 이 부분이 중간 자리
  ├─ Segment 0
  ├─ Segment 1
  ├─ ...
  └─ Segment FF
[ Log ID 1 ]
  ├─ Segment 0
  ├─ Segment 1
  └─ ...
```

## 마지막 8자리

마지막 8자리(`0000000B`)는 위 예시와 같이 세그먼트id이며 물리적인 개념의 LSN이다.

# 세그먼트 파일명 규칙

세그먼트 파일명이 어떻게 관리되는지 간단히 정리하면

- 16진수 한 자리는 `0 ~ F`까지 사용
- `F` 다음은 끝이 아니라 `10`으로 넘어감
- 그래서 `0F` 다음은 `10`, `1F` 다음은 `20`
- `FF`는 16진수로 `255`

PostgreSQL 기본 WAL 세그먼트 크기가 16MB라면 Segment ID는 보통:

```
00000000
~
000000FF
```

까지 사용하고, 그 다음에는 Log ID가 1 증가하면서 Segment ID가 다시 `00000000`부터 시작합니다.

즉:

```
...000000FE
...000000FF
...00000100000000
```

처럼 넘어간다고 보면 됩니다.

```sql
select * from pg_ls_waldir() order by modification desc limit 5;
```

해당 쿼리를 이용해서 현재 WAL 세그먼트 파일을 볼 수 있다.

쉽게 보면 **WAL 세그먼트 파일 안에 여러 개의 WAL 레코드가 차곡차곡 들어간다**는 설명입니다.

구조를 단순화하면:

```
WAL 세그먼트 파일
 ├─ Page
 │   ├─ WAL Record
 │   ├─ WAL Record
 │   └─ WAL Record
 ├─ Page
 │   ├─ WAL Record
 │   └─ WAL Record
 └─ ...
```

그리고 WAL Record 하나는 다시 이렇게 나뉩니다.

```
WAL Record
 ├─ Header
 │   ├─ LSN
 │   ├─ 레코드 크기
 │   ├─ 트랜잭션 ID
 │   └─ 기타 메타정보
 │
 └─ Data
     ├─ 실제 변경 내용
     ├─ 어떤 페이지를 변경했는지
     └─ 어떤 작업을 했는지
```

예를 들어 이런 SQL이 실행됐다고 보면:

```
UPDATE account
SET name = 'kim'
WHERE id = 1;
```

PostgreSQL은 대략 이런 WAL Record를 남깁니다.

```
Header
 ├─ LSN: 이 WAL 레코드의 위치
 ├─ Transaction ID
 └─ 크기 등의 정보

Data
 ├─ account 테이블의 특정 페이지
 ├─ 특정 레코드
 └─ name 값이 변경됨
```

여기서 **LSN**은 쉽게 말해 WAL 안의 주소입니다.

```
WAL
───────────────────────────────────────>

레코드 A       레코드 B       레코드 C
LSN 100        LSN 200        LSN 300
```



## WAL 페이지 구성 요소

- **Page Header** : 각 페이지의 메타데이터를 저장한다. 여기에는 페이지 번호, 페이지 크기, 타임라인 ID, 체크섬, 페이지의 시작 위치를 나타내는 LSN 등이 포함된다.
- **Magic Number**: WAL 파일 형식을 식별한다.
- **Page Size 및 Version**: 페이지의 크기 및 버전 정보를 저장한다.
- **Log Sequence Number(LSN)**: 이 페이지의 위치를 나타낸다.
- **Page Number**: 파일 내에서 페이지의 위치를 나타낸다.
- **Previous Page Pointer**: 이전 페이지의 번호를 가리키는 포인터이다.
- **Timeline ID**: 페이지가 속한 타임라인을 나타낸다.
- **CRC32 Checksum**: 페이지 무결성을 확인하기 위한 체크섬
- **XLog Record** : 실제 트랜잭션 데이터가 저장되는 영역이다.
- **Page Trailer** : 페이지의 마지막 부분에 대한 정보를 저장한다.



## WAL 레코드의 구성요소

- **레코드 헤더** : 각 트랜잭션 레코드의 메타 데이터를 저장한다.
- **XLogRecPtr** : 레코드의 시작 위치를 가리키는 LSN 정보를 저장한다.
- **XLog record Type** : 레코드의 유형 정보(삭제, 변경, 입력 등)를 저장한다.
- **XLog record Length** : 레코드의 길이에 대한 정보이며 레코드의 끝을 식별하는 데 사용된다.
- **Checkpoint Information** : 레코드의 복구 시점을 기록한다.
- **Previous LSN** : 이전 레코드의 위치를 나타내는 LSN 정보를 저장한다.
- **Record Version** : 레코드의 형식이나 구조의 버전을 나타낸다.
- **XLog data** : 실제 트랜잭션 데이터.
- **CRC checksum** : 데이터 손상을 감지하는 체크섬(CRC) 정보를 저장한다.



WAL 세그먼트에서 LSN은 파일에 기록된 각각의 트랜잭션 레코드의 위치를 식별하기 용이하도록 사용되고 있으며 복구 및 변경 사항을 추적하는데 필요한 정보를 저장하고 있다. LSN은 전체 64비트로 구성되며 상위/하위 각각 32비트로 나눠진다.

![image-20260905120234748](/images/postgresql-wal-mechanism/img_3.png)

근데 나는 64비트, 32비트 왜 나눠지는지 궁금해서 클로드에게 물어봤다.

결국 LSN은 64비트로 이루어져있고 이게 사람의 눈으로 보기 힘들어서 사람이 읽기 쉽게 반으로 잘라서 보여준다고 한다.

예를들어 3,725초(sec) 라는 값이 있으면 1:02:05  (1시간 2분 5초) 로 사람이 보기편하도록 변환한 값과 비슷한 맥락으로 보면 된다.

다시 내용으로 돌아와서 LSN의 상위 32비트는 logID를 의미한다. 고유식별자이며 순서유지를 위하여 존재한다.

하위 32비트는 로그 파일 내에서 위치를 의미한다.

```
AAAAAAAA / BB CCCCCC
└──┬───┘   ┬  └──┬──┘
 로그 ID   │   세그먼트 파일 안에서의 바이트 위치
           │   (6자리 16진수 = 최대 16MB)
           │
      세그먼트 번호
      (2자리 16진수 = 0~255, 즉 256개)
```

LSN의 구조이며 앞에서 설명한거대로 앞자리 8자리는 logID, 뒷자리중에서 앞 2자리는 세그먼트 번호 -> 즉 이 로그 파일에서 몇번째 세그먼트 인지 의미, 나머지 뒷자리 6자리는 그 세그먼트 파일의 몇 바이트째인지 의미

그래서 나는 이걸 한번 추적해봤다.

![image-20260912114056564](/images/postgresql-wal-mechanism/img_4.png)

1,2번 항목은 최근 WAL LSN을 기준으로 해당 LSN을 이용해서 WAL를 저장하는 파일의 이름을 출력하고 해당 WAL파일에서 몇번째 offset에 위치하는지 알 수 있다.
3번 항목은 실제 pg-data의 wal 디렉토리에 존재하는지 찾아보았다.

Pg_walfile_name 컬럼의 값이 디렉토리에도 존재하는점을 확인하였다.



## pg_current_wal_lsn, pg_current_wal_insert_lsn

```sql
select pg_current_wal_lsn(),
       pg_current_wal_insert_lsn();
```

pg_current_wal_lsn는 마지막으로 사용된 LSN값이고 pg_current_wal_insert_lsn는 디스크에 기록되기 전 현재 버퍼에 삽입된 데이터의 논리적 위치를 알 수 있다.
 
![image-20260925141200512](/images/postgresql-wal-mechanism/img_5.png)

조회결과를 보면 WAL 파일에 저장된 LSN과 버퍼에 입력된 LSN이 동일하다.

LSN 정보는 0, 0C, 000B70 으로 구분된다.

```
Log ID: 0
WAL 세그먼트 파일 명: 0C
LSN 오프셋(16진수): 000B70
```



근데 나는 이게 이해가 잘안가서 클로드한테 이해하기 쉽게 도서관을 예시로 들어달라고 했다.

`0/C0000B70`를 예시로 들자면

0 -> 도서관 0층을 간다.

0C -> 0C번 책을 꺼낸다.(책 표지: 00000001000000000000000C)

000B70 -> 책내용을 처음부터 읽어서 000B70 번째 글자로 이동한다.(해당값을 10진수로 바꾸면 2928이 오프셋)

## pg_switch_wal

현재 사용되고 있는 WAL 세그먼트 파일을 종료하고 새로운 WAL 세그먼트 파일과 LSN값을 반환한다.

```sql
select pg_switch_wal();
```

해당 함수를 이용해서 백업 및 복구에 필요한 시점을 사용자가 원하는 시점으로 생성하고 싶을때 사용된다.



## pg_wal_lsn_diff

서로 다른 lsn 사이의 크기 차리를 구하는 함수이다. 출력값은 숫자의 바이트 크기를 반환한다.

책에서는 pg_current_wal_lsn, pg_last_wal_replay_lsn 함수를 이용해서 출력했는데, null이 뜨는것이다. 이걸 GPT에게 물어봤는데 일단 pg_last_wal_replay_lsn 함수의 결과값이 null이 나오는것은 즉 해당 pg서버는 primary라는 것이다.

```sql
select pg_is_in_recovery();
```

해당 결과값이 false로 나오면 해당 서버는 primary라는 의미이며 원본서버라는 것이다.

즉, pg_last_wal_replay_lsn 함수는 복제서버가 원본서버의 WAL를 어디까지 따라왔는지 알 수 있는 함수라는 것이다.

정리하면 내가 테스트하고 있는 환경은 원본서버(primary)여서 복제서버(replica)에서만 사용하는 pg_last_wal_replay_lsn 함수를 사용하면 null이 출력되어서 pg_wal_lsn_diff 함수를 통해서 비교값을 알 수 없는 상태이다.

이걸 일단 내눈으로 확인하기 위해서 직접 lsn값을 넣어서 비교해봤다.
